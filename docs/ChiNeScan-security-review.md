# ChiNeScan product security review

Review date: 2026-11-06. This is a focused source and regression-test review of the current local application, not a penetration test or proof of security.

## Deployment and trust model

- The dashboard is an explicitly started local service. `chinescan/cli/commands.py` starts Uvicorn on `127.0.0.1` with one worker. The app middleware also checks both the request Host and peer address for loopback. This is not a supported remote or multi-tenant deployment.
- One local operator account is supported. `chinescan/core/accounts.py` holds in-memory sessions and auth-epoch checks; operator credentials are local files. A process compromise has the privileges of the logged-in operating-system user.
- Local scan input is selected by the operator through CLI, configured project paths, or guarded local dashboard workflows. Source text, filenames, archives, imported reports, and external-tool output are untrusted. Normal code assessment does not execute target application code or install its dependencies.
- Optional scanner integrations execute configured external executables. `chinescan/scanners/external.py` uses argument arrays, `shell=False`, timeouts, output bounds, and a restricted environment. Network-backed package audits require explicit consent. GitHub import and chain/domain workflows have separate outbound paths and explicit configuration/authorization controls; they are not part of ordinary local code scanning.
- ChiNeScan can read files the operator explicitly selects plus its own config, database, report, and managed-work directories. Authorization within this single-operator process is not an OS sandbox and does not limit the logged-in operator's file privileges.

## Verified fixes in this continuation

- Corrected incorrect user-facing branding and report headings; retained `chinescan` command, imports, environment keys, API paths, and database compatibility. Added a test assertion for the dashboard ChiNeScan label.
- Added a CLI `report --format detail` that prints finding explanation rationale and the score contribution ledger; report Markdown also includes explanation fields and each score contribution.
- Corrected API download handling so a complete JSON report can use its documented 20 MiB bound instead of being rejected by the generic 2 MiB attachment helper. The 10,000-finding cap now also applies to CLI `full-json` through the shared report renderer. Errors are explicit and return no attachment.
- Changed the JWT `alg=none` keyword candidate from Critical to High/Possible with a contextual explanation. Critical severity is not emitted by the built-in source-text ruleset because this scanner cannot establish the required verification behavior and exposure from a static token match.

No product vulnerability was fixed by the earlier implementation. Release validation performed on 2026-11-06 found a redaction performance issue; see the release validation report for the controlled timing evidence and reproduction. This follow-up supersedes the earlier statement that no issue had been verified. The rest of this document remains a source/test scoped review, not a penetration test.

## Release validation follow-up — 2026-11-06

`chinescan/core/logging/redaction.py::_KEY_ASSIGNMENT` contains an unbounded lookahead and applies redaction before truncation. In a local Python 3.12.10 timing probe over benign repeated `x` characters, `redact()` took 0.0046 s for 100 characters, 0.0614 s for 500, 0.1803 s for 1,000, 0.7970 s for 2,000, and 2.4316 s for 4,000. A synthetic 20 MiB report render did not complete during the bounded observation window and was stopped. This is consistent with superlinear regex work; it is not a general benchmark or a proof of a specific asymptotic bound.

The authenticated external report import accepted up to 2 MiB and `external_reports._text()` called `redact(cleaned)` before slicing imported descriptions/remediation to 2,000 characters. At review time, this was a verified resource-exhaustion risk for untrusted imported text; no correction had yet been made during that verification-only release phase.

### R1 remediation status — 2026-11-06

The risk described above was remediated in the subsequent R1 pass. Redaction now uses a forward delimiter scan, external text is clipped before retained content is redacted, and shared per-operation limits fail closed. Synthetic canary tests verify CLI/API failures do not return the original unredacted input. See [the R1 remediation report](reports/redaction-remediation-2026-11-06.md) and [release closure validation](reports/release-closure-2026-11-06.md). This resolves the reproduced redaction-work pattern for the documented operation bounds; it is not a formal complexity proof, load test, or guarantee against all resource exhaustion.

## Container scan remediation follow-up — 2026-11-07

The release container scan reported HIGH findings for apt/libapt-pkg7.0 and
zlib1g. The image now uses digest-pinned Python 3.12.16 slim Trixie, which
provides apt and libapt-pkg7.0 3.0.4, and installs the Trixie security update
of zlib1g (`1:1.3.dfsg+really1.3.1-1+deb13u1`). Local package inspection
confirmed those versions. The runtime image also includes the Alembic
configuration and migration files needed for SQLite initialization. A local
image build and loopback `/api/health` check succeeded. The local Trivy
rescan did not complete: vulnerability database downloads from the official
registries were throttled to tens of KiB/s, so no local scan result is
claimed. The pull request's equivalent container scan must complete
successfully before merge. This is a narrow container remediation record,
not a general security certification.
