# API security hardening report

Audit performed on branch `hardening/api-security`. `.env` files and secret values were
not opened, printed, or logged.

| Feature | Status | What changed / audit result | Tests added or inspected | Known gaps |
| --- | --- | --- | --- | --- |
| F1 SQL injection | PARTIAL | `SQLiteRepository` uses SQLAlchemy expressions and bound values for reads, writes, filters, and `IN` queries. Sort and filter fields are selected from per-record allowlists. | Existing tests reject invalid sort/filter values; repository has no raw request-built SQL. | Requested injection payload matrix for `ids`, search, and filters was not added. |
| F2 unsafe deserialization | PARTIAL | No `pickle`, `marshal`, `shelve`, `eval`, `exec`, `yaml.load`, or `shell=True` found in application paths. YAML detection rules use `yaml.safe_load_all`; parsers apply format-specific validation and some byte/file caps. | Existing indicator, log, import, and configuration tests cover parser errors and caps. | No unified depth cap or complete malicious YAML/nesting/oversized-file test matrix across every importer. |
| F3 request filtering / mass assignment | PARTIAL | Mutating request models inspected use Pydantic `extra="forbid"` and bounded fields; role/profile update fields are not present. | Existing request validation tests cover weak passwords and malformed bodies. | Dedicated unknown-field matrix (`role`, `is_admin`, `auth_epoch`, `status`) was not added for every mutating endpoint. |
| F4 response filtering / sensitive data | PARTIAL | Reviewed read routes generally declare response models; path-free summaries and shared redaction are already present. Error logs avoid submitted bodies and use safe route metadata. | Existing redaction canaries, path-free report, and response contract tests. | Not every GET route was walked with a sentinel in both response bodies and captured logs; a complete route-wide guarantee is unverified. |
| F5 XSS / output encoding | PARTIAL | No direct `dangerouslySetInnerHTML`, `innerHTML`, or frontend `eval` use found. Report renderers HTML-escape text, Markdown escapes untrusted text, and downloads are generated as attachments. Security headers are added by the common response middleware. | Existing tests verify script-like report inputs are escaped and attachment headers are set. | The requested dedicated Vitest finding-title text-render test and `javascript:`/`data:` API URL test were not added. |
| F6 authentication | PARTIAL | Existing in-memory `ProgressiveLockout` applies generic login/reset responses with account and client keys; successful login clears throttle state. Sessions are process-local, bounded by TTL, revoked on logout, and invalidated by auth epoch changes after credential reset. | Existing auth tests cover unknown-user response parity, lockout, logout, reset, and session invalidation. | Optional TOTP was skipped to avoid adding credential lifecycle and CLI enrollment complexity; absolute plus idle expiry is not separately implemented/verified. |
| F7 rate limiting | PARTIAL | Existing in-process controls limit diagnostics, project actions, filesystem browsing, imports, and authentication. | Existing lockout and endpoint throttle tests. | No general route-class middleware, configurable limits in `Settings`, bounded shared bucket eviction, or standardized `Retry-After` 429 response was implemented. |
| F8 authorization / IDOR | PARTIAL | API reads and writes are generally protected by session dependencies; mutating operations use CSRF. IDs are treated as opaque strings and records are fetched with both type and ID predicates. Filesystem operations use capability-based browsing and reports are generated in memory. | Existing unauthenticated API, CSRF, filesystem policy, and path traversal tests. | No complete route enumeration test or single wrong-record-type cross-route test. Multi-user ownership requirements remain future work. |
| F9 gateway / routing / versioning | APPLY | No gateway or JWT added. `/api/v1/*` rewrites to existing `/api/*` routes. Responses include `X-API-Version: 1`; API/deployment docs describe compatibility and proxy TLS/rate-limit configuration. | Added `test_v1_api_alias_uses_existing_auth_and_reports_version`; verifies parity for unauthenticated scans and rejects `/api/v2`. | Alias behavior test currently compares the unauthenticated 401 contract; authenticated payload parity is not separately asserted. |

F9 gateway and JWT replacement are NOT-APPLICABLE: ChineScan is a single local operator
application with server-side revocable cookie sessions and no downstream services to protect.
The deployment example is documentation only; it does not change the loopback default.

Multi-user support would require an owner field on each object plus per-object ownership checks
on every read, write, export, and job-control route before adding additional accounts.
